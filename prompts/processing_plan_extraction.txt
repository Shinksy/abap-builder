<operation_schema>
Operation schema:

- LOOP: source, into, steps, optional iteration_scope
- READ: source, into, conditions
- IF: conditions, then, else
- MOVE: source, target
- CALCULATE: expression, target, sources
- DERIVE: expression, target, sources
- TRANSFORM: source, target, transformation
- AGGREGATE: source, target, function, group_by, sources
- COUNT: source, target, group_by, distinct
- AVERAGE: numerator, denominator, target, group_by
- PERCENTAGE: numerator, denominator, target, group_by
- CLEAR: target
- APPEND: source, target
- CALL_FUNCTION: name, input_parameters, output_parameters
- CALL_STATIC_METHOD: class, method, input_parameters, output_parameters, receiving_parameter or returning_parameter
- CALL_METHOD: object, method, input_parameters, output_parameters, receiving_parameter or returning_parameter
- CONCATENATE, SORT, DELETE: include only required fields
</operation_schema>

<optional_technical_detail_fields>
Optional technical-detail fields may be added to any processing step:

- data_object: the exact table, work area, structure, component list, callable result, output object, or runtime object being processed.
- iteration_scope: "internal_table_rows", "runtime_structure_components", "runtime_type_components", or another specific collection scope.
- derived_or_modified_value: the value, field, variable, component, output object, or state changed by the step.
- retained_state: intermediate state that must survive for later steps, such as totals, counters, flags, lookup results, field symbols, component metadata, or per-component widths.
- dynamic_runtime_operation: runtime type discovery, structure discovery, component discovery, dynamic component access, dynamic assignment, per-component calculation, or other dynamic ABAP concept required by the specification.
- technical_details: concise implementation-relevant prose when the structured fields alone are not enough.
</optional_technical_detail_fields>

<rules>
Rules

- Preserve the order of the functional specification.
- Preserve distinct structures, internal tables, work areas, runtime component lists, and loop scopes as distinct processing steps. Do not collapse separate operations into generic wording such as "Loop through the source data".
- For every LOOP, identify whether it iterates internal-table rows, runtime structure components, runtime type components, callable results, output fields, or another specific collection.
- For every step, identify what data/object is processed, what value is derived or modified, what state must be retained for later processing, and any dynamic runtime operation needed by the specification.
- When the specification requires dynamic ABAP behavior, preserve the dynamic concepts explicitly in the optional technical-detail fields and in separate ordered steps. This includes runtime type or structure discovery, runtime component discovery, iteration over structure components, iteration over internal-table rows, dynamic component access, and per-component calculated state such as column widths.
- Do not prescribe specific SAP classes, function modules, or methods for dynamic runtime behavior unless the validated processing contract or specification explicitly requires a named callable.
- Extract only business logic explicitly described.
- Translate business actions into the corresponding processing operations:
  - "Process each record" → LOOP
  - "Search", "Find", "Lookup" → READ
  - "Populate", "Assign", "Use" → MOVE
  - "Call function/module" → CALL_FUNCTION
  - "Call static method", "class method", "=&gt;" -&gt; CALL_STATIC_METHOD
  - "Call instance method", "object method", "-&gt;" -&gt; CALL_METHOD
  - "Add output record" → APPEND
- Translate calculation and summary words into executable processing operations:
  - "Calculate", "compute", formulas, margins, differences, ratios -&gt; CALCULATE
  - "Derive", "determine", "classify", "bucket" -&gt; DERIVE
  - "Transform", "format", "convert", "substring", "concatenate" -&gt; TRANSFORM or CONCATENATE
  - "Total", "sum", "aggregate" -&gt; AGGREGATE
  - "Count", "number of", "distinct documents" -&gt; COUNT
  - "Average", "mean" -&gt; AVERAGE
  - "Percent", "percentage", "rate" -&gt; PERCENTAGE
- Do not invent business logic that is not implied by the specification.
- Nest all steps that occur within a LOOP inside its steps array.
- READ conditions must be structured lookup-key objects with left, operator and right.
- For READ operations, include only fields required to locate a row in the already-populated internal table.
- Do not put SQL WHERE filters, selection parameters, select-options, constants, or predicates already applied during SELECT into READ conditions.
- The processing generator may assume internal tables already contain only rows that passed database extraction filters.
- Only fields explicitly required to be read or returned should appear in processing fields.
- Fields used only in SQL WHERE conditions are filter fields and must not be added to processing structures or output structures unless explicitly required elsewhere in the specification.
- IF branches must contain then and else arrays. Use empty arrays when a branch has no explicit steps.
- Output fields must be referenced as w_output-&lt;field&gt;.
- Every required output field must have a concrete MOVE, CALCULATE, DERIVE, TRANSFORM, AGGREGATE, COUNT, AVERAGE, PERCENTAGE, or callable output step targeting w_output-&lt;field&gt;.
- For one-output-row-per-group requirements, include group_by on the aggregation/count/average/percentage steps and do not model the output as one APPEND per source record.
- For calculations, include a classical ABAP-compatible expression using only available source fields, constants, declared variables, or prior aggregate results.
- For percentages and averages, include the numerator and denominator and any required zero-denominator handling implied by the specification.
- When an output record is created:
  - CLEAR w_output before populating it.
  - APPEND w_output TO t_output after it is populated.
- CALL_FUNCTION must contain separate input_parameters and output_parameters objects.
- CALL_STATIC_METHOD and CALL_METHOD must contain separate input_parameters and output_parameters objects.
- For CALL_STATIC_METHOD, split the provider-compatible CLASS=&gt;METHOD identity into class and method.
- For CALL_METHOD, use the instance object name and method name from the specification.
- Use receiving_parameter when a method returns a value via ABAP RECEIVING.
- Use returning_parameter when the specification describes a returned value without naming ABAP RECEIVING syntax.
- receiving_parameter and returning_parameter are target variables or fields that receive the returned value; do not put them inside input_parameters or output_parameters.
- Do not use placeholder conditions.
- Do not use placeholder processing steps.
- Return an empty processing_steps array only if the specification contains no business-processing logic and no required output fields are derived by processing.
</rules>
